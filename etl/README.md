# Relocation Finder ETL — Phase 1

> **Status: first live run completed 2026-09-20.** All four sources fetched,
> joined, validated with 0 FAIL / 0 WARN, and published to
> `public/data/counties.json` (3,144 rows × 33 columns). **Rebuilt 2026-09-26:**
> all 50 states + DC (3,144 rows; Alaska and Hawaii are opt-in in the app).
> Climate is measured from population centers; every county outside Alaska has
> every climate column, and 4 remote Alaska areas have none.
> Vintages: ACS 2023
> (2019–2023), BEA RPP 2024, SEDA 6.0, NOAA 1991–2020 normals. See
> [Known gaps](#known-gaps) for what the data does *not* cover.

Builds one CSV — one row per US county — by joining four federal/academic
data sources onto a common geographic key.

This is Phase 1 of the project described in `Working Master Plan.md` at the repo root. Read
that first for the why; this document covers the how.

---

## The point of this phase

Four agencies describe American geography four different ways:

| Agency | Organizes by | Publishes RPP/data at |
|---|---|---|
| Census | Counties, tracts, places | County and below |
| BEA | Metro areas (CBSAs) | State, metro, non-metro portion |
| Stanford (SEDA) | School districts | District, county, metro, state |
| NOAA | Weather stations | Point locations (lat/lon) |

**Phase 1 exists to prove these can be reconciled onto one spine.** Nothing
downstream — scoring, ranking, mapping — is worth building until that works.
If the join holds, every future metric is just another column.

## Quick start

```bash
cd etl
pip install -r requirements.txt

cp .env.example .env
# Fill in CENSUS_API_KEY and BEA_API_KEY — both free, both instant:
#   https://api.census.gov/data/key_signup.html
#   https://apps.bea.gov/API/signup/

# SEDA is a manual download — see the SEDA section below.

python -m etl.test_offline        # offline suite, no network needed
python -m etl.build               # the real thing
```

Output lands in `data/out/counties.csv` and `counties.json` (one readable
object per county). When validation passes, the same table is published to
`public/data/counties.json` in a **compact columnar format** —
`{format, columns, rows}`, floats rounded per column (see
`build.to_app_payload`), ~700 KB instead of 2.6 MB, small enough for the
service worker to cache offline. That is the file the Next.js app reads and
the one that gets committed, so the app builds without Python. A build that
fails validation never touches it. If you change the published shape, bump
`APP_PAYLOAD_FORMAT` and `PAYLOAD_FORMAT` in `src/lib/scoring/dataset.ts`
together.

## Architecture

```
  Census Gazetteer ──────────► data/interim/spine.csv     (the county list)
                                       │
  Census ACS API ────────────► acs.csv │
  BEA RPP API + CBSA xwalk ──► bea.csv │  all LEFT JOINed
  SEDA (manual file) ────────► seda.csv│  onto the spine
  NOAA normals ──────────────► noaa.csv│
                                       ▼
                              join.py + derived columns
                                       │
                                  validate.py
                                       ▼
                          data/out/counties.{csv,json}
```

### Three ideas worth understanding before changing anything

**1. The spine decides what exists.** The Census Gazetteer produces the
authoritative county list. Every other source is LEFT joined onto it. A source
missing a county leaves nulls; it never removes a row. An inner join anywhere
would silently shrink the dataset to whatever the worst-covered source has, and
nothing would tell you.

**2. Every source runs independently.** Each writes its own tidy file to
`data/interim/` before anything is joined. A broken source doesn't block the
others, you can inspect one source's output in isolation, and re-joining after
a parsing fix takes seconds instead of a re-fetch.

**3. Raw responses are cached on disk.** `data/raw/` holds every HTTP response
keyed by URL hash. Iterate on parsing without re-hitting anyone's API; an
interrupted NOAA run resumes. Delete the directory to force a refresh.

Two rules keep the cache honest, both enforced inside `util.http_get`:
filenames are built from the URL *path only*, so an API key in the query
string never lands on disk; and a body that fails the caller's `check` hook
(BEA wrapping an error in a 200, Census answering 204) is never written —
and if one is already there from before, it is evicted and re-fetched.
Pass a `check` for every new JSON source; do not parse-then-validate in
the caller.

### Directory layout

| Path | Contents | Safe to delete? |
|---|---|---|
| `data/raw/` | Cached HTTP responses, downloaded files | Yes — forces re-fetch. **Except** a manually downloaded SEDA file. |
| `data/interim/` | One tidy CSV per source, post-parse pre-join | Yes — regenerated by a fetch |
| `data/out/` | Final joined artifacts (canonical; what `validate.py` reads) | Yes — regenerated by a join |
| `../public/data/counties.json` | Compact columnar copy for the app; written only on a green build | Committed — don't delete casually |

## Output schema

One row per county, 3,144 rows (50 states + DC).

| Column | Type | Notes |
|---|---|---|
| `fips` | string | 5 chars, zero-padded. **The join key.** |
| `county_name` | string | e.g. "Travis County" |
| `state` | string | Two-letter USPS |
| `lat`, `lon` | float | Internal point (guaranteed inside the polygon) — roughly the geographic middle |
| `pop_lat`, `pop_lon` | float | 2020 population-weighted center — where people live. Null for CT's 9 planning regions (the 2020 file predates them) |
| `land_sq_mi` | float | Land area |

### Census ACS 5-year
| Column | Unit |
|---|---|
| `population` | people |
| `median_home_value` | dollars, owner-occupied |
| `median_household_income` | dollars |
| `median_gross_rent` | dollars/month, includes utilities |
| `aggregate_real_estate_taxes`, `aggregate_home_value` | dollars, owner-occupied (B25090, B25082). Inputs to `property_tax_effective_rate`; kept in `data/out/`, left out of the app payload |

### BEA Regional Price Parities
| Column | Notes |
|---|---|
| `rpp_all` | Blended index, 100 = national average |
| `rpp_rents` | Housing rents component |
| `rpp_utilities` | Separate since BEA's Dec 2021 revision |
| `rpp_goods` | |
| `rpp_services` | "Other services" — no longer includes utilities |
| `rpp_geo_level` | `metro` / `state` — **provenance, don't drop**. ~38% / ~62%. |
| `rpp_source_geo` | Which geography the value came from |

### SEDA
| Column | Notes |
|---|---|
| `school_achievement` | Grade levels above/below national average. `0.42` ≈ four-tenths of a grade ahead. Typical range −2 to +2. |

### NOAA 1991–2020 normals
| Column | Unit |
|---|---|
| `summer_high_f` | °F, mean of Jun/Jul/Aug daily maxima |
| `winter_low_f` | °F, mean of Dec/Jan/Feb daily minima |
| `spring_mean_f`, `fall_mean_f` | °F |
| `annual_precip_in`, `annual_snow_in` | inches/year |
| `hottest_month_high_f`, `coldest_month_low_f` | °F — the peak and trough of the year (plan §6 *Climate preferences*) |
| `days_above_90f`, `nights_below_32f` | Average days/nights per year past the threshold |
| `rainy_days` | Days/year with ≥ 0.01 in precipitation |
| `snow_days` | Days/year with ≥ 1.0 in snowfall |
| `climate_point` | `population` or `internal` — which point the station search started from |
| `climate_station_id` | Nearest contributing station |
| `climate_station_dist_mi` | Distance to it — **use this to flag low-confidence values** |
| `climate_station_count` | How many stations were averaged |

`data/interim/noaa_monthly.csv` for the Phase 6 climate tab.

### Derived
| Column | Formula | Reading |
|---|---|---|
| `home_value_to_income` | `home_value / income` | ~3 historically normal, >6 severely unaffordable |
| `rent_to_income` | `rent×12 / income` | 0.30 is the conventional threshold |
| `price_to_rent` | `home_value / (rent×12)` | <15 favors buying, >20 favors renting |
| `real_income` | `income / (rpp_all/100)` | Purchasing-power-adjusted income |
| `property_tax_effective_rate` | `100 × aggregate_real_estate_taxes / aggregate_home_value` | Percent of home value paid in property tax per year. Aggregates because the median-taxes variable (B25103) is top-coded at $10,000+. State totals match Tax Foundation's Facts & Figures Table 33 within 0.1 point. |

State laws and taxes are a separate pipeline — see `LAWS.md` and `etl/laws/`.

## Source notes

### Census ACS — `sources/acs.py`

**5-year estimates, not 1-year.** The 1-year release only covers geographies
above 65,000 population, which drops roughly two-thirds of US counties. Not a
close call.

**Vintage is discovered, not assumed.** Census publishes each December and
availability dates move. The module starts at `config.ACS_YEAR`, walks
backwards until a release responds, and logs which it used. The chosen vintage
is written to the output as `acs_vintage` — surface it in the UI.

> ⚠️ **The sentinel trap.** The Census API does not return nulls. It returns
> jam values like `-666666666`. Skip the cleaning step and a county with no
> median rent gets a rent of negative 666 million, which passes silently
> through percentile ranking and anchors an extreme of every derived metric.
> `util.clean_census_nulls` handles it. `validate.py` fails the build if any
> escape. Do not remove either.

### BEA RPP — `sources/bea.py`

This is the most intricate module. Read its docstring before editing.

**BEA does not publish county-level RPP**, and — despite what its interactive
tables imply — **it does not publish a per-state non-metro portion either.**
Verified 2026-09-20 against the Regional API's GeoFips lists for SARPP and
MARPP *and* the bulk downloads (`apps.bea.gov/regional/zip/{SARPP,MARPP}.zip`):
the only portion row anywhere is `00999 United States (Nonmetropolitan
Portion)`, national. So every county inherits a value by one of two rules:

1. County is in a **metropolitan** CBSA → that CBSA's RPP (`metro`, ~38%)
2. Otherwise → the **statewide** RPP (`state`, ~62%)

Which rule fired is recorded per county in `rpp_geo_level`.

> Micropolitan CBSAs appear in the Census delineation file but BEA does **not**
> publish RPP for them (its footnote: "Nonmetropolitan portion includes
> micropolitan counties"), so they deliberately fall through to rule 2.
> MARPP uses OMB bulletin 23-01 delineations — the same 2023 vintage as our
> crosswalk, which is why every metro county matched on the first run.

**Two precision losses, both known and recorded:** every county in a metro
shares one number (Travis and Williamson both get Austin's), and every
non-metro county gets its state's *blend* — which includes that state's
metros and so runs somewhat high for rural areas, most in states dominated
by one expensive metro (CA, WA, CO, NY, MA). For relative ranking this is a
loss of resolution, not a wrong ordering; rural counties in a state tie with
each other as they would under any state-level rule. `rpp_geo_level` lets
the UI say so. Both are why we store components. A derived state non-metro
value (statewide minus its metros, by BEA's expenditure weights) is deferred.

If BEA ever adds per-state portions, `_classify_state_rows` still detects
them by GeoName and they take precedence as level `nonmetro`; `validate.py`'s
bound would then need revisiting.

> ⚠️ **Line codes and GeoFips are discovered at runtime, not hardcoded.** Both
> have changed across BEA methodology revisions and neither is reliably
> documented anywhere stable. The module calls `GetParameterValuesFiltered`,
> matches line descriptions against keyword patterns, and **logs the mapping
> it resolved**.
>
> **If you are QA-ing this pipeline, that logged mapping is the single most
> important thing to verify on first run.** If matching fails, the error lists
> everything BEA offered so you can fix `COMPONENT_PATTERNS`.

**Why `rpp_utilities` exists with no UI slider.** Product decision: utilities
are not a filter criterion. The column is stored anyway because the
tract-level recombination needs all four components to reassemble a correct
index after overriding rents with ACS data. **Don't delete it because it looks
unused** — that would silently break the Phase 5 path.

**Expenditure weights are deliberately not hardcoded.** BEA derives them from
PCE and ACS housing-rents expenditures; any figure quoted from memory is
wrong. Phase 1 doesn't need them — we store components as published and BEA's
own `rpp_all` is the authoritative blend. When the tract path needs to
recombine, read the weights from BEA's methodology release.

### SEDA — `sources/seda.py`

**Manual download.** SEDA gates files behind a download page and direct URLs
change between versions. One download every few years isn't worth automating
badly.

1. Go to <https://edopportunity.org/opportunity/data/downloads/>
2. Download the most recent **county-level, pooled, cohort-standardized (CS)**
   file — something like `seda_county_pool_cs_5.0.csv`
3. Save it into `etl/data/raw/`
4. `python -m etl.sources.seda` — it auto-detects `seda*county*.csv`

**Column names change between versions.** The module tries a candidate list
and logs what it picked. Verify that line. It also warns if the median
absolute value looks unlike a cohort-standardized scale, which is the
signature of grabbing a raw score column by mistake.

**Two honest caveats:**
- *School districts don't nest inside counties.* SEDA's county rollups
  aggregate districts within each county. Fine for "which counties have strong
  schools", inadequate for "which district should I target".
- *The data lags.* Main releases cover ~2008–09 through 2018–19. Acceptable for
  relative ranking — district quality is sticky — but say so in the UI.

### NOAA — `sources/noaa.py`

**Why this is in Phase 1:** every other source is a dictionary lookup on FIPS.
NOAA needs a real spatial join. It's the most likely thing to break, so it
belongs in the phase whose job is proving the join works.

**How the join works:** drop the CoCoRaHS network (`US1…` ids — volunteer
rain gauges, no temperature, 5,440 of 15,615 stations) from the inventory;
find the 10 nearest remaining stations within 60 miles of each county's
**population center** (2020 Census; the internal point for the 9 Connecticut
planning regions, which the 2020 file predates); fetch them; then, **separately for each variable group**
(temperature, precipitation, snowfall), keep the nearest 3 stations that
actually report it and average those weighted by inverse distance. Any
county still short of 3 stations for some group gets a **fallback search**:
the 40 nearest within the same 60 miles, fetched and re-selected.
`climate_station_*` columns describe the temperature stations. Averaging
several stations smooths out station-specific quirks (an airport station on
a runway apron reads differently from one in a park two miles away) while
inverse-distance weighting keeps the nearest dominant.

> **Why the two filters exist (first run, 2026-09-20).** The original design
> took the 3 nearest stations *before* knowing which had temperature data.
> ~42% of NOAA stations are precipitation-only, and CoCoRaHS gauges are
> densest exactly where people live — Madison County AL (Huntsville) had
> ten of them closer than its airport station and came out **null**, as did
> Maricopa (Phoenix) and Pulaski (Little Rock). Candidates-then-usable plus
> the `US1` exclusion fixed all three. Keep both.
>
> **Why selection is per variable (review, 2026-09-22).** The first-run fix
> kept only stations with temperature and threw the rest away. Many
> temperature stations don't report snowfall, so 214 counties — snowy ND and
> MN ones included — had null snow while a nearby station reported it. And
> Livingston Parish LA (next to Baton Rouge) had *no* climate because all
> 10 candidates were rain gauges. Per-group selection plus the K=40
> fallback addresses both without leaving NOAA.

The full run fetches ~9,100 station files, plus ~225 more in the fallback
search, once (threaded, ~10 minutes) and caches them; re-runs from cache take
about three minutes.

> ⚠️ **What this does not do:** elevation adjustment, or interpolation that
> respects terrain. In a mountainous county the nearest station may be at a
> very different elevation. A proper job would use PRISM gridded data rather
> than point stations. This is a deliberate Phase 1 simplification —
> `climate_station_dist_mi` is stored per county so the UI can flag
> low-confidence values. **Note this before anyone makes a decision based on a
> mountain county's numbers.**

## Validation

`validate.py` runs after every build. It exists to catch failures that produce
*plausible-looking* output — the ones you'd never notice:

| Check | Catches |
|---|---|
| Row count in range | Joins that dropped rows, or merges that fanned out |
| FIPS integrity | Duplicates, wrong length, missing low-FIPS states |
| **Per-source join rates** | The leading-zero bug, per source (see below) |
| Census sentinels | Jam values that escaped cleaning |
| Spot-check counties | Hand-picked counties spanning the range |
| Plausible ranges | Unit errors (rent in dollars vs. hundreds) |
| Derived recomputation | A formula edited in one place but not the other |
| **Zero-join is FAIL** | A source whose interim file exists but matches <5% of counties — a broken key, even for an optional source |
| **RPP assignment mix** | `state` above 66% (derived: share of counties outside a metro CBSA, plus margin) or metro below 15% — CBSA codes and MARPP aren't lining up |

Severity: **FAIL** → exit 1 · **WARN** → build completes · `--strict` promotes
warnings to failures.

### The FIPS leading-zero bug

County FIPS are 5-character **strings** with meaningful leading zeros. San
Francisco is `"06075"`, not `6075`. Let pandas infer the dtype anywhere and it
becomes an int, the zero vanishes, and every join against it silently drops
all ~600 counties in states with FIPS < 10 — AL, AK, AZ, AR, CA, CO, CT, DE,
DC, FL, GA.

The failure is nasty because it's *partial*: you still get ~2,900 rows,
everything looks fine, and California is just… gone.

> **This bug was found in this validator during development.** The original
> version checked the *spine's* FIPS integrity — but the spine is built from
> one clean source and is always fine. The bug corrupts the **merge**, and a
> 19% null rate sailed under a global 50%-null warning threshold as ordinary
> sparse data.
>
> The fix (`_check_source_join_rates`) tests each source's join rate *within
> the low-FIPS band separately*. A source covering 95% of high-FIPS counties
> but 0% of low-FIPS ones isn't sparse data — it's a broken key, and that's
> unambiguous. `test_offline.py` injects the bug and asserts it's caught.
> Keep that test.

## First run

Expect friction. In likely order:

1. **Keys.** `CENSUS_API_KEY` and `BEA_API_KEY` in `.env`.
2. **SEDA file.** Manual download; the module tells you exactly what to fetch.
3. **BEA line-code mapping.** Verify the logged mapping. This is the highest-value
   thing to eyeball.
4. **CBSA delineation URL.** The URL changes with each OMB revision. If it 404s,
   `load_cbsa_crosswalk()` documents a manual CSV fallback.
5. **NOAA inventory URL.** Path changes between product versions; the error
   points at the product page.
6. **NOAA runtime.** First run fetches thousands of station files. Minutes.
   Cached afterwards. Use `--limit 200` to smoke-test first — it writes
   `data/interim/noaa_smoke.csv`, never the canonical `noaa.csv`, so a stub
   can't be picked up by `build --skip-fetch`. More than
   `MAX_TRANSPORT_FAILURES` non-404 errors aborts the run rather than
   producing a mostly-null table; re-run to resume from cache.

Recommended sequence — get each source green before joining:

```bash
python -m etl.sources.spine     # no keys needed, should just work
python -m etl.sources.acs       # needs Census key
python -m etl.sources.bea       # needs BEA key; CHECK THE LINE-CODE MAPPING
python -m etl.sources.seda      # needs the manual file
python -m etl.sources.popcenter # no key; must run before noaa
python -m etl.sources.boundaries # map shapes; needs Node (runs npx mapshaper)
python -m etl.sources.noaa --limit 200
python -m etl.sources.noaa      # full run
python -m etl.build --skip-fetch
```

### Known rough edges

- **Alaska** uses boroughs and census areas. It is in the data again since
  2026-09-26 (it was excluded 2026-09-22 → 09-26 via `EXCLUDED_STATES` in
  `sources/spine.py`, now empty); whether it is scored is an app toggle.
  Known gaps, shown as unknown: 4 remote areas have no weather station within
  60 mi, and Chugach / Copper River (the 2019 Valdez-Cordova split) have no
  SEDA school data.
- **Louisiana** uses parishes. They have FIPS so the join works, but
  spot-check them.
- **Connecticut** replaced its 8 legacy counties with 9 planning regions.
  Census products from 2022 on (Gazetteer, ACS) use the new codes
  (`09110`–`09190`); legacy `09001` Fairfield no longer exists in them.
  `09190` Western Connecticut is in the spot-check list for this reason.
  See "Known gaps" for the SEDA consequence.
- **Territories** (PR, GU, VI, AS, MP) are dropped by default —
  `DROP_TERRITORIES` in `sources/spine.py`. Most other sources don't cover
  them, so they'd be mostly-null noise.
- **Independent cities** (Virginia especially) are county-equivalents with
  their own FIPS. Handled, but they behave oddly in per-capita metrics.

## Known gaps

Deliberate Phase 1 omissions, not oversights:

- **No ACS margins of error.** The `M` variables exist alongside every `E`. For
  small counties the MOE can be enormous. Worth pulling so the UI can gray out
  unreliable values. See `config.ACS_VARIABLES`.
- **No elevation-aware climate.** See the NOAA section.
- **No non-housing `real_income` variant.** `rpp_all` includes rents, so scoring
  on both `real_income` and a housing metric double-counts housing. The fix
  needs BEA's expenditure weights. Tracked in `Working Master Plan.md`.
- **Nulls stay null — by design.** The ETL never imputes. Decided
  2026-09-22: the app treats a missing value as *unknown* — grey on the map,
  with a toggle to show or hide unknown results (`Working Master Plan.md` §6).
  So a null is always better than a guessed number here.
- **Snowfall is the weakest climate column.** Fewer stations report it than
  temperature or rain. It is a low-priority metric; remaining nulls are
  accepted and shown as unknown.
- **No boundaries.** Phase 4 pulls TIGER and simplifies with `mapshaper`.
- **No state-level non-metro cost of living.** BEA publishes none (API or
  bulk — verified 2026-09-20), so ~62% of counties carry their state's blended
  RPP, which runs somewhat high for rural areas. See the BEA section. A derived
  value is possible but deferred.
- ~~San Francisco's climate comes from the wrong stations.~~ **Fixed
  2026-09-26** along with the wider problem it was an instance of: climate
  was measured at each county's geographic middle, which for big western
  counties is nowhere near where people live (San Diego read 84 days over
  90°F from an inland point; now 19). The station search now starts from the
  2020 Census population center — see `sources/popcenter.py`. SF's nearest
  station went from 28.8 mi to 0.9 mi.
- **County climate is one point per county.** Even from the population
  center, a county spanning coast and desert gets one set of numbers. That is
  a county-level limit, not a bug; the tract-level roadmap addresses it.
- **Connecticut has no `school_achievement`.** SEDA keys counties by the
  legacy FIPS (`09001`–`09015`), while the spine uses the planning regions
  Census adopted in 2022 (`09110`–`09190`). The LEFT join therefore leaves
  all nine CT rows null for that one metric. *Confirmed on the first live run,
  2026-09-20: 9/9 CT rows null for `school_achievement`, every other metric
  present.* A fix would be a legacy-county → planning-region crosswalk
  with area- or population-weighted averaging; not done in Phase 1. The UI
  should treat CT school data as "unavailable", not "zero".

## For another agent picking this up

Read in this order:

1. `Working Master Plan.md` at repo root — project context and the decisions already made
2. This file
3. `config.py` — every tunable in one place
4. The docstring of whichever `sources/*.py` you're touching — each explains
   what it produces, why that source, and what's fragile about it

**Conventions that matter:**

- FIPS is a **string**, always. Every `read_csv` gets `dtype=str` on key
  columns. Every FIPS passes through `normalize_fips()`.
- Every merge is a **LEFT join onto the spine**. No exceptions.
- Add a metric → add it to `join.COLUMN_ORDER` and, if it has a sane range, to
  `config.PLAUSIBLE_RANGES`.
- Uncertain API constants get **discovered and logged**, not hardcoded. See
  `bea.discover_line_codes` for the pattern.
- `Working Master Plan.md` says: *if this file and the code disagree, the code is right and
  the doc is stale.* Same rule here.

**If you change a derived formula**, update it in three places or the
validator will catch you: `join.add_derived_columns`, the table in this file,
and `Working Master Plan.md` §5.
